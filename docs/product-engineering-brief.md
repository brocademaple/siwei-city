# 思维城邦产品与工程说明

## 项目定位

思维城邦是一个面向知识工作者的“议题推理工作台”。它把用户的模糊议题或零散想法转化为结构化思维地图，并通过多角色建议和结构巡检，推动用户形成下一步行动和可导出的讨论报告材料。

这个项目的重点不是做一个普通笔记应用，而是验证一个更具体的产品假设：

> AI 时代的信息生成越来越便宜，但个人真正需要沉淀的是问题谱系、判断结构、反例约束和行动回流。

## 为什么值得做

传统 AI 问答很容易给出一个“看起来完整”的答案，但用户很难知道：

- 这个答案依赖哪些证据？
- 哪些反驳没有被处理？
- 哪些判断只是直觉？
- 下一步最小行动是什么？
- 本轮讨论能否沉淀成可复用报告？

思维城邦把这些隐性结构显性化：观点变成建筑，论证关系变成道路，角色建议变成居民来函，结构缺口变成巡城官令。

## 当前完成度

当前版本已经完成可运行 MVP：

- Vite + React + TypeScript 单页应用。
- panorama 城邦地图和建筑式观点节点。
- 本地开局推演：议题输入后生成问题、假设、证据缺口、反驳、行动。
- 建筑详情弹窗和道路关系创建。
- 多角色建议流，支持预览和采纳。
- 巡检规则，定位结构缺口。
- 首次进入新手指引和常驻任务线。
- 自有美术资产接入和素材质量检测。
- GitHub Pages 自动部署配置。

## 产品设计亮点

### 1. 用户保留最终判断权

角色建议只预览，不自动改变地图；巡城官令只提示问题，不自动修复。这避免了 AI 工具常见的“越俎代庖”，让系统保持协作而不是接管。

### 2. 把抽象推理转成空间化界面

用户不需要阅读长列表来理解讨论状态。观点位置、建筑类型、道路关系和巡检提示共同构成一张可扫视的认知地图。

### 3. 面向闭环而不是面向记录

MVP 主链条是：

```text
输入材料 -> 开局推演 -> 观点建筑 -> 居民建议 -> 采纳入城 -> 铺设道路 -> 巡城官令 -> 收束产物
```

最终目标是地图、下一步行动和报告材料，而不是单纯保存笔记。

## 前端工程亮点

- 使用 React 状态管理完成无后端原型闭环。
- 数据模型明确区分 `IdeaNode`、`Route`、`District`、`RoleContribution`、`ReviewFinding`。
- 巡检逻辑独立在 `src/lib/review.ts`，便于后续测试和 AI 接入。
- 开局推演逻辑独立在 `src/lib/opening.ts`，便于替换为真实模型调用。
- 美术资产集中在 `src/assets/art.ts`，正式 UI 不直接引用 raw 生成母图。
- 构建前通过 `scripts/check-green-artifacts.mjs` 检查正式素材是否残留明显绿幕像素。
- GitHub Pages 使用 Actions 构建部署，主分支保持源码干净。

## 视觉与交互策略

视觉方向是“希腊罗马修道院学院 + 游戏式知识城邦”：

- 温暖羊皮纸、青金石蓝、青铜和陶土色作为基础色。
- panorama 背景提供第一屏记忆点。
- 建筑图标承载观点节点，不用普通卡片堆叠。
- 地图内弹窗承载详情和关系操作，避免把主体验拆成表单后台。
- 新手指引降低理解成本，把城邦术语翻译成功能动作。

## 下一步规划

### P0：收束报告

增加“生成报告草案”按钮，输出 Markdown：

- 当前议题
- 观点列表
- 道路关系
- 巡检问题
- 下一步最小行动

### P1：本地保存和多条导入

- 支持多行想法导入。
- 用 `localStorage` 保存当前城邦状态。
- 支持重置和恢复。

### P2：真实 agent 接入

- 实践者补证据。
- 研究者补假设。
- 怀疑者补反例。
- 执行者补行动。

保持“建议先预览，用户确认后入城”的产品原则。

### P3：地图内角色建筑

把右侧列表迁移为地图内居民席位和巡城官塔，让角色建议与系统诊断真正成为城邦的一部分。

## 核心取舍

- 先做单机 MVP，是为了验证核心交互闭环，不在账号、协作和后端上过早投入。
- 先用本地 seed 模拟 agent，是为了验证“多角色建议是否能帮助用户推进判断”。
- 先做 GitHub Pages，是为了让项目能够被直接体验，而不是只停留在代码仓库。
- 美术资产进入仓库前做检测，是为了保证生成式素材不会把临时绿幕带到产品界面。

## 关键假设

- 用户愿意用空间化界面整理复杂议题。
- AI 对个人知识管理的价值，不在于替用户保存更多内容，而在于帮助用户维护判断结构。
- 一份可交付的思考产品，至少需要地图、行动和报告材料三种结果。
