# 居民圆桌机制设计

## 机制目标

居民圆桌现在发生在议会内景中。它的目标是把多 agent 从“并列建议列表”推进成“彼此回应的讨论过程”。每一轮发言都应该回答三个问题：

- 谁在说？
- TA 回应了谁？
- 这句话应该如何改变地图？

## Agent 角色

| 角色 | 职能 | 典型输出 |
| --- | --- | --- |
| 研究者 | 补证据、找案例、提出可验证判断 | 数据、案例、验证指标 |
| 怀疑者 | 找反例、失败条件和风险 | 冲突观点、风险假设 |
| 实践者 | 把议题放回真实场景 | 用户场景、触发条件、阻力 |
| 执行者 | 收束行动和取舍 | 最小行动、优先级、决策条件 |

## 空间承载

当前版本把空间分成两层：

- 城邦全貌：展示居民角色图鉴、prompt 摘要和讨论沉淀结果。
- 议会内景：承载主要观点碰撞、采纳、巡城和卷轴查看。

四位居民、巡城官和卷轴官都有独立角色图像与 prompt 摘要，集中定义在 `src/lib/residents.ts`。

## 居民池与上桌代表

当前版本不把议会角色写死成一组固定男性队列，而是维护一个完整居民池：

- 每个功能角色都有至少两种具体人格。
- 具体人格包含性别呈现、性格描述、发言风格、prompt 摘要和输出契约。
- 每轮真正坐上议会桌的是 `councilResidentIds` 里选出的代表。
- 城邦全貌的建筑图鉴展示完整居民池，议会内景展示本轮上桌代表。

第一版上桌组合保持男女各三位：

| 上桌居民 | 功能角色 | 主要差异 |
| --- | --- | --- |
| 证据制图师 | 研究者 | 女性角色，制作证据地图和判断阈值 |
| 反证怀疑者 | 怀疑者 | 男性角色，寻找最强反例 |
| 场景实践者 | 实践者 | 男性角色，把议题放回真实一天 |
| 推进执行官 | 执行者 | 女性角色，收束最小可逆行动 |
| 结构巡城官 | 巡城官 | 男性角色，检查结构断点 |
| 报告编辑官 | 卷轴官 | 女性角色，编辑可带走报告 |

## 三种固定模式

### 探索模式

用户意图：我还不知道问题是什么。

顺序：

1. 问题
2. 研究者找证据
3. 怀疑者找反例
4. 实践者给场景
5. 形成可继续探索的问题谱系

适合：议题模糊、方向未定、需要打开可能性。

### 决策模式

用户意图：我需要做取舍。

顺序：

1. 问题
2. 研究者提出判断
3. 怀疑者挑战风险
4. 执行者列取舍条件
5. 输出推荐方案

适合：要不要做、先做哪个、方案怎么选。

### 行动模式

用户意图：我需要马上推进。

顺序：

1. 问题
2. 实践者拆真实场景
3. 执行者给最小行动
4. 研究者补验证指标
5. 输出行动计划

适合：已经想推进，但卡在第一步。

## 回应对象

每条圆桌发言记录 `respondsTo`：

- 核心问题
- 上一位居民
- 某座观点建筑
- 巡城官令

这样用户能看见 agent 不是各说各话，而是在同一条讨论链上互相回应。

## 冲突与道路

每条发言可以建议一条道路关系：

- 支持：证据或判断支撑另一个观点。
- 冲突：反例、风险或失败条件挑战另一个观点。
- 依赖：一个观点成立需要另一个条件。
- 延伸：从判断推进到行动、问题或新假设。
- 回流：行动结果需要回到证据或假设中验证。

## 采纳机制

所有 AI 或本地模板发言先进入“来函/圆桌记录”。用户点击“采纳入城”后才会：

1. 生成正式观点建筑。
2. 点亮新建筑。
3. 按建议关系生成道路。
4. 更新卷轴馆中的圆桌记录和报告。

这保证 AI 不越权，用户始终保留编辑和采纳权。

## 最终沉淀

卷轴馆沉淀四类 Markdown：

- 本轮讨论报告
- 下一步行动计划
- 居民圆桌记录
- 巡城修缮记录

历史城邦会进一步保存整轮状态，让每个议题都成为可回看的项目档案。
